# SNBT → BB：3×3×3 范围与分块坐标

日期：2026-11-24。状态：代码已实现、已构建，通过自动测试；未替换安装版或正式发行，BB 实际打开仍待用户确认。

## 两种模式

完整蓝图最多跨越 **3×3×3 个单位方块格子**，整体与分块模式采用相同限制。

- **导出 BB 整体**：一个 Java Block/Item 工程，保持方向与尺寸。默认将占用格范围中心放在 `[8,8,8]`，保留小方块在格子内的偏心位置；3 格范围适配 Java `[-16,32]`。
- **导出 BB 分块**：按原游戏方块网格裁切，每个非空 1×1×1 格生成独立工程，最多 27 份；各份局部模型坐标为 0..16。

选择文件和粘贴文本均适用。用户只需保存一次完整蓝图。超过范围时两种模式均拒绝整次导出，不缩小、不截断，也不能通过选择分块绕过限制。
此前首轮允许大蓝图任意批量拆分的行为已收紧；先前 5 格高雨棚等样例不再符合本轮入口规则。

范围按实际几何跨越的原游戏网格计算，不只看几何宽度：例如从 -1/16 到 47/16 跨越 4 格，即使宽度为 3 方块也拒绝。
上边界恰好落在格线时不多算一格；空的外圈不计入范围，内部空隙保留。

## 坐标标记

X 正向为东、Y 正向为上、Z 正向为南。保持这些轴向，不旋转、交换轴或翻转符号。
以各轴最小占用格组成的角点为系内原点，拆分格坐标各分量为 **0..2**。
例如源坐标 `(10,-2,4)` 到 `(12,0,6)` 标为 `(0,0,0)` 到 `(2,2,2)`。
若只有首末两格有内容，输出 `(0,0,0)` 和 `(2,0,0)`，不把末格压缩成 `(1,0,0)`。

输出 `<name>_blocks/block_<x>_<y>_<z>.bbmodel`，每个工程内部也记录 `reader_block_grid.block`。
`blocks.bbmanifest.json` schema 2 包含：

- `block`：0..2 系内坐标；`grid_size`：实际格数，各轴 1..3。
- `source_origin_block`：归一化前的系内原点；每项的 `source_block` 保留原坐标供追溯。
- `axes`：游戏轴向；`coordinate_space` 为 `normalized_game_axis_block_grid`。
- `source_min_blocks`：源蓝图 min 信息，只作追溯，不用于改变拆分格线。

拼回系内位置使用 `block*16 + 工程局部坐标`；回到源蓝图使用 `(source_origin_block+block)*16 + 工程局部坐标`。
每份不能分别居中。整体工程的 `reader_block_grid` 记录原点、格数和平移量。

## 保留与限制

标准长方体跨格裁切，保留材质、颜色、原方块内 UV 相位及可表示的面 UV 变换。子结构按各自 grid 换算；高精度保留小数，16 模型单位不是网格精度上限。
材质 PNG 内嵌，动画材质取第一帧；角点偏移、斜面和缺失材质拒绝整批导出。门动画不输出。
分块保留闭合面；百万裁切片段的资源上限继续保留。输出只是 BB 工程，不包含 MCreator 多方块放置逻辑或直接 Java JSON。

整批仍可记录历史、重导出及打包 zip。校验在落盘前完成；同名批次拒绝覆盖。原蓝图和存档不变。

## CLI 与验证

`output.format: "bbmodel"` 配合 `output.split: "none"`（默认）导出整体；`split: "blocks"` 导出分块。
`normalize_scale` 必须 false。分块忽略 center，整体 center 指占用格范围居中。
核心能力增加 `bbmodel_max_blocks_per_axis: 3`、`bbmodel_local_grid: true`，App 两种入口均检查，旧核心需更新。
成功整体返回 `bbmodel`，分块返回 `bbmodel_manifest`。

App 仓库执行 `python tests/test_bbmodel_blocks.py`：覆盖完整 27 格、两种模式超限拒绝、负坐标及远原点归一化、空隙保留、边界裁切、UV、高精度子结构、失败不落盘、历史重建与 zip。
C++ 的 BB exporter 测试与既有两代 SNBT、动画贴图、现代素材测试一并回归。
