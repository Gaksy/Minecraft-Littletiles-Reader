# LittleTiles → MCreator 静态模型工作流审查

审查日期：2026-11-23。依据本地 Reader 与 reader-app 源码、现有文档及 Blockbench／MCreator 官方资料。仅完成需求与代码审查，未实现新导出器，未执行 Blockbench／MCreator／游戏端验收。

## 1. 已确认范围

用户确认：只保留 LittleTiles 的几何结构和材质，不迁移门动画、开关、交互或其他结构行为。门等结构作为静态模型处理；采用哪一个静态姿态仍需通过真实样本确认，不能假定读取结构文件就是游戏里当前打开的姿态。

需求实质是：用 LittleTiles 作为游戏内建模工具，把作品转为独立方块模组可用的静态模型资源。Reader 负责提取和转换，MCreator 负责注册方块、配置行为与打包 MOD。

建议工作流：

1. 游戏内用 LittleTiles 制作作品，并用蓝图／结构文件明确导出对象。
2. Reader 读取结构与对应素材，执行目标格式兼容检查。
3. Reader 导出 Java 方块 JSON + PNG，同时可选导出可编辑的 `.bbmodel`。
4. 用户可选在 Blockbench 检查模型和 UV；合格模型直接导入 MCreator。
5. MCreator 配置方块属性、碰撞／选框和放置方式，构建 MOD。
6. 在目标游戏版本验收几何、材质、比例、朝向和显示效果。

不应把“必须在 BB 转换一次”设为固定环节；若工具已经保证目标格式合法，BB 是检查／编辑工具。

## 2. 现有能力与缺口

| 环节 | 当前代码情况 | 本需求的增量 |
| --- | --- | --- |
| 读取 LT 作品 | 已有存档 `.mca`、SNBT `.txt/.struct` 入口，识别两代结构方言 | 首版优先结构文件，减少把周围地形一起导出的风险 |
| 几何 | 已有 grid 换算、盒子、逐角偏移、裁剪与子结构几何 | 区分可直接转为 JSON 的盒子与不兼容几何 |
| 材质 | 六面贴图、tile 染色与 tint 烘焙，生成端组合原版／模组／资源包素材 | 保留采样和 UV 语义；检查缺失贴图；输出自足资源 |
| 输出 | 当前模型链路写 OBJ + MTL + PNG；另有 SNBT 互转 | 新增 Java 方块 JSON／BB 导出器与兼容报告 |
| 桌面端 | 已有项目、素材管理、导出记录与自足 ZIP | 新增导出目标、版本配置、锚点和兼容性结果 |
| MCreator | 未发现专用导入适配或端到端验收证据 | 固定 Minecraft、加载器、MCreator 及生成器版本完成验收 |

这是在现有读取与材质能力上扩展导出目标，不能视为只改输出扩展名。

## 3. 需要保留的技术边界

### 几何表达能力

`.bbmodel` 是 Blockbench 工程容器，能保存工程不等于能导出 Java 方块模型。MCreator 官方要求普通 Java 方块／物品采用 Blockbench 的 Java Block/Item 工作区。

轴对齐的小长方体适合直接生成 JSON elements。LittleTiles 的任意逐角偏移、楔形、不规则裁剪多面体不能普遍无损转成该格式；某些旋转长方体可能可表达，但应单独识别，不把所有偏移形状视为旋转盒子。

建议首版遇到不兼容形状时给出可定位的错误报告，保留原始输入；不静默删除、拉直或改成近似形状。后续才考虑显式启用的体素近似或网格导出路线。

Blockbench 官方格式表列出 Java Block/Item 的尺寸与旋转约束，并注明 1.21.6 以前旋转角受限。应按目标 Minecraft 版本建立规则，不能把新版编辑器能保存的能力套用到所有旧版。

### 多方块尺寸与游戏行为

必须分清：

- 一个方块承载一个更大的静态外观：只改变模型，并不会自动让所有视觉覆盖位置拥有独立碰撞、选框与占位行为。
- 整体作品自动切成多个局部模型：工具可规划批量拆分与文件命名，但 JSON 文件集合本身不会实现一次放置、关联破坏或跨位置占位。

本轮移除 LT 行为迁移后，以上放置／碰撞行为仍由 MCreator 负责。如果首版只交付静态模型资源，应明确写出这一边界。建议先验收单方块范围的作品，再扩展按方块网格自动切分；跨边界时重算局部坐标和 UV，并保留分片偏移清单。

### 材质与“所见即所得”

复用游戏素材可减少手绘，但 Reader 并非截图或光影烘焙工具。现有材质链路处理基础贴图、tint 和 tile 颜色，不包含完整光影、反射、阴影、环境光及所有资源包扩展。

生成端当前把素材压缩为六面贴图与 tintindex：`Resolver.model()` 每个方向只取第一层，`faces_of_blockstate()` 优先 normal／首个变体；该表没有完整保留源模型逐面的 UV 矩形、旋转和所有状态变体。因此，非标准方块、overlay、CTM 等不能承诺与游戏完全一致。若这些属于目标用户常用素材，需要扩展素材契约，不能只补 JSON 写出器。

建议将优势表述为：“在游戏内完成建模与外观预览，导出静态几何和基础材质；最终效果在目标 MOD 中验收。”

首版允许多张 PNG，单张图集是独立需求。若采用图集，需要重映射 UV、处理边缘采样和跨格重复，不能简单拼图。颜色已经烘焙后应避免目标模型再次叠加同一染色。透明 PNG 仍需在 MCreator 设置并验证对应渲染方式。

### 单位、原点与依赖

Reader 的 OBJ 当前以方块为单位，并允许居中、最长边归一化。新方块导出应保留真实比例，以明确锚点换算到模型坐标；通常一方块边长对应 16 模型单位。不能直接沿用把最长边压到 1 的选项。

若输出包含完整几何与独立 PNG，目标模型原则上可以不在运行时依赖 LT；是否还依赖源模组或资源包，取决于输出是否继续引用其资源，必须在游戏中验证。素材来源和对外分发许可需单独记录。

## 4. 实现建议

在解析层之后、合并为 OBJ 网格之前引入共享的静态场景表示，保留层级／来源标识、grid、局部坐标、材质与颜色、盒子及偏移信息。再按导出目标分流：

- 既有 OBJ：继续走任意多面体网格链路。
- Java 方块 JSON：仅接受规则允许的几何，输出模型与贴图。
- BB 工程：与 JSON 共用同一场景、材质与变换，避免两个导出结果不一致。

可复用 `LtStructure::Group/Node`、`TileEntity`、素材组合与 `MaterialManager` 的烘焙逻辑，但当前烘焙入口与 OBJ 建造器有耦合，需提取共享接口。不要先把全部结构导成 OBJ，再尝试从合并网格逆推出原始小方块。

现有 ZIP 路径会收集 OBJ／MTL／贴图，新格式需要扩展产品清单与打包逻辑，不能默认现有 ZIP 已覆盖 JSON／BB。

MCreator 提供 OBJ 导入路线，可作为短期兼容试验。官方文档要求三角化等约束，而 Reader 明确保留 n-gon，写面时没有输出法线索引，不能认定当前 OBJ 已可直接验收。应针对具体加载器／生成器检查三角化、材质、UV 和光照，而非默认 OBJ 在全部版本可用。

## 5. 推荐首版与验收

首版：结构文件输入；静态轴对齐盒子；基础不透明材质与 tile 染色；真实比例与明确锚点；Java JSON + 多 PNG；可选 BB 工程；不兼容报告。先选定一组 Minecraft／加载器／MCreator／生成器版本验收，再扩大支持矩阵。

| 样本 | 验收内容 |
| --- | --- |
| 单盒与六面不同图案 | 坐标、朝向、六面 UV，无镜像或转向错误 |
| 混合材质与颜色的多个小盒子 | 不丢盒子、不串材质、不重复染色 |
| 子结构不同 grid | 相对比例和位置正确 |
| 跨方块边界结构 | 按选定策略完整导出或明确拒绝，不能自动缩小 |
| 逐角偏移／楔形 | 给出来源与不兼容原因，不输出伪成功 |
| 门结构 | 只输出约定静态姿态，不携带行为；与游戏参考姿态对照 |
| 缺失素材 | 明确标识来源和影响，不沿用上一块材质冒充正确 |

最终验收应包含：Blockbench 打开／编辑（若支持 BB）、MCreator 导入与构建、目标游戏中放置和六面观察；脱离源 LT 环境后检查资源完整性。透明／发光材质、体素近似、自动分片和多方块联动作为后续独立范围。
